# Slice 1.5 evidence: JUNO governs Claude Code and MCP, and every journal is anchored

**Slice:** 1.5 (spec v0.6.1, §4.3 "Ingress modes, and what each does not protect"; build plan `docs/plans/slice-1.5-build-plan.md`).
**Merged increments:** 1 (canonical scope, PR #31), 2 (the operator's key, anchored heads, PR #35), 3 (what untrusted content can choose, PR #36), 4 (Claude Code's hook, mode C, PR #43), 5 (the MCP gateway, mode B, PR #46), 6 (§4.3's acceptance end to end, PR #48).
**How it was proven:** `make verify` in CI on every merged head (unit tests, then sealed containers), and `make mediated-e2e` in a cloud session with the real Claude Code binary. **No paid model was called** in any acceptance test: model turns are scripted (D-002, D-145), and the containers that run Claude Code have no network.

## In five lines

1. **JUNO now governs three ways in** (§4.3): its own loop (mode A), Claude Code through a hook it cannot turn off (mode C), and an MCP server behind JUNO's gateway (mode B). All three admit sessions, count calls and park through one shared session layer (D-194).
2. **§4.3's four acceptance tests pass together, in one `make verify` run with §18's five**, and again with the real Claude Code binary: a write outside the grant is denied; an injected shell command parks; an injected recipient parks and is never sent; a forged grant is not honoured.
3. **Every journal is now copied off the host** (§3.4.1, D-198): every mode, at most a minute apart and when a service stops. A session whose journal cannot be copied stops. The operator's `juno journal check` passes for every session the tests ran.
4. **Authority comes only from your key** (§3.2): grants are signed by a key kept off your computer and loaded into Windows' key agent only while you sign (D-214). A tampered grant, one signed by another key and an unsigned one are each refused in modes A and C, and a tampered one in mode B.
5. **What JUNO cannot see, it cannot govern.** The limits below are stated plainly: above all, a Claude Code session you start on Windows itself is not governed, and your Windows account is trusted like your key.

## What untrusted content can and cannot choose (§2.2.2)

"Untrusted" means anything the model wrote, read or was steered by. Your constants and values from sources you trust are not affected.

| Effect | Where it goes (target) | What it says (payload) |
|---|---|---|
| read | can choose anything inside the grant's scope | can choose |
| write | can choose a path only inside a reversible workspace you named, checkpointed before the first turn; anywhere else parks `integrity_floor` | can choose, up to the capability's ceiling |
| external (send, post, push) | cannot choose, unless the grant lists that exact value | can choose the wording, up to the ceiling |
| irreversible (delete, pay) | cannot choose, unless the grant lists that exact value | can choose, up to the ceiling |
| any | never chooses which program runs | — |

## What each mode does not protect (§4.3)

### Mode A — JUNO's own loop
JUNO runs the model and every call, in sealed containers (no network, non-root, no capabilities, CPU, memory and process limits). It does not protect (§4.3):
1. **A compromise of the host beyond what signing and anchoring cover** (§3.2, §3.4.1): a kernel or container-runtime escape, or something that takes over the runner. Signed grants mean it cannot fake permission; anchors mean it cannot quietly rewrite what was anchored.
2. **Code that reaches a program by a way other than the call's arguments** (§2.3.1): for example a program that reads instructions from a file it is allowed to read. JUNO judges which program runs and with which arguments, not what that program then does with its inputs.
Two more, not in §4.3's table but true of mode A:
3. **What a call is allowed to do.** A read inside the grant can read everything the grant covers; a write inside a reversible workspace changes it (you can restore the checkpoint).
4. **The model's own reasoning.** JUNO judges what the model asks to do, never what it thinks.

### Mode C — Claude Code with JUNO's hook
JUNO's hook judges every **tool call** Claude Code makes. It does not govern:
1. **Anything Claude Code does without a tool call:** its own memory, and the text of a file you `@`-mention if Claude does not then read it with a tool. The install turns direct `@`-insertion off (D-139), so a mentioned file is read through the Read tool, which JUNO judges.
2. **A file or symlink changed between JUNO's check and Claude Code's use of it.** Claude Code, not JUNO, performs the effect. Keep the workspace out of reach of anything else.
3. **How Claude Code is started (D-173).** JUNO governs a session only when you start Claude Code in the governed WSL terminal, as `juno-agent`, with the hooks in the root-owned managed settings. **A session started on Windows itself, or by another program, or with `CLAUDE_CODE_MANAGED_SETTINGS_PATH` naming another folder, is not governed: JUNO never sees it.** No governed tool call can change any of this.
4. **A shell function named with a program's absolute path.** JUNO hands Claude Code the command rebuilt with absolute paths (D-152), so `PATH` and aliases do not choose the program, but a shell startup file could define `function /usr/bin/cat { … }`. Keep `juno-agent`'s startup files free of functions.
5. **Steering and context:** a hook session cannot be steered (§7.8), and JUNO does not see the tool descriptions Claude Code reads.
6. **Tokens and money:** Claude Code's own limits govern them; you accept that when you admit a session.
7. **A hard link made after JUNO's check** (the gap in item 2). Hard links that exist at the check are detected (D-157).
8. **A public-looking web name that leads to a private server**, if you list the public internet as a source (D-164). List exact sites instead if your intranet uses such names.
9. **Everything mode B does not protect** (and so everything mode A does not), plus the residuals of running on your Windows machine (below).

### Mode B — an MCP server behind JUNO's gateway
§4.3: everything mode A does not protect, plus the following.
1. **Context ownership and steering** (§7.8). The client, not JUNO, owns the conversation; a gateway session cannot be steered.
2. **Tool descriptions.** The gateway passes the server's tool descriptions to the model unchanged; an injected instruction there reaches the model. What it can make the model *do* is still judged: an unlisted recipient parks.
3. **What the server does with an allowed call.** JUNO journals the call and the answer, but cannot see or undo what the server does inside its own systems.
4. **The server's own credentials and network.** They are the server's, set in your gateway session file; JUNO never shows them to Claude Code, but does not limit what the server reaches with them.
5. **Anything Claude Code does outside MCP and the hook.** In a session governed by the hook too, the hook covers Claude Code's own tools. Without JUNO's hook, only the gateway's calls are governed.
6. **Other MCP servers in a session without JUNO's hook and managed files.** The protections against them hold only where `juno hook install --gateway` installed them and `juno hook check --gateway` passed.
7. **An in-process (`sdk`) MCP server** registered by an app that starts Claude Code. Claude Code applies no list to it; JUNO's hook denies its calls, and a governed session is started from the WSL terminal, where no app registers one.
8. **How Claude Code is started** (as mode C item 3).
9. **Server-to-client requests and multi-step answers** are refused, not supported (D-186). A server that needs them does not work through the gateway.

## Residuals recorded during Slice 1.5, in plain words

Each is a limit JUNO states rather than hides. Where a decision number is given, the full reasoning is there.

**Running on your Windows machine (D-130, D-173)**
1. **Your Windows account is trusted like your signing key.** Any program running as you on Windows, an AI agent or coding tool run there included, can ask Windows' key agent to sign a grant while your key is loaded, and can start WSL as root at any time, and so undo everything JUNO does. A governed Claude Code runs in WSL as `juno-agent`, with interop and drive mounting off, so it has no channel to Windows or to your key agent. The guide narrows the window (D-214): its first box, "Rules for your Windows account", and Part B load the key from its off-machine backup only to sign and remove it straight after (`ssh-add -D`, then `ssh-add -l` shows none). This narrows D-093; it does not close it: while the key is loaded, and at every moment for WSL's root, a program running as you is trusted like you.
2. **A kernel or WSL escape** (root in the WSL2 kernel, an escape from the VM to Windows, or an attack from the distribution on a Windows network service) is not protected.
3. **Your signing key's agent** never exports the key, but signs for any program running as you while it holds the key (D-093). And it does not hold the key only in memory: Microsoft's OpenSSH maintainers state that Windows' agent stores every key added with `ssh-add` in the user's registry, encrypted, and keeps it across restarts until it is removed (D-216). So the key is on this computer's disk for as long as it is loaded; `ssh-add -D` removes it from the agent, and whether Windows leaves traces of the encrypted copy on the disk afterwards is not something JUNO can check. The guide keeps that time to the minutes of a signing (D-214).
4. **The runner's "cannot write the trust anchor" check does not work on Windows itself** (D-124), where it refuses to start (fail-closed); the runner runs only in WSL.
5. **The trust anchor's check** looks at the file `/etc/juno/operator.pub` and its own folder, not the folders above it (D-116, D-194; a reviewer note on PR #35). Part E puts it in `/etc/juno`, root's, under root's `/etc`.

**The journal and its anchors (§3.4.1, D-122, D-126, D-198)**
6. **Up to one interval of recent history can still be rewritten** by something that can write the journal's storage: entries written since the last anchor (at most a minute by default) are not yet protected. `juno journal check` reports them as "unanchored", never as verified.
7. **A compromised host can stop JUNO or withhold new entries** (§3.4.1's own residual). It cannot fake past entries that were anchored.
8. **The anchors depend on GitHub and the network.** If the anchor repository cannot be reached, sessions stop (fail-closed): availability, not safety.
9. **The push key is on the host.** Anything that takes over `juno-runner` can push new anchors. It cannot take a pushed commit back out (the repository's ruleset blocks force-push and deletion), but it can push an ordinary commit that deletes or changes anchor files. JUNO reads the repository's whole history at every start and refuses a repository where that ever happened (D-204). Your GitHub account, which can change the ruleset, is trusted like your Windows account.
10. **A running service does not compare a task's chain with the stored anchors before each resume** (D-126). Every start does compare the whole journal with its anchors (D-201); a rewrite under a running service is caught by the next anchor, the next start and `juno journal check`.
11. **A record deleted from the journal is found at the next start** when it had been anchored: the journal's own record names every record, and the deleted one's anchors remain (D-202). One deleted before its first anchor is item 15.

**Paths and reads (D-113, D-157, D-162, D-164, D-174, D-178)**
12. **A read that meets more than 64 shortcuts** counts at your highest class, so a listing over a large `node_modules` can be stopped under a low clearance (a cost, not a gap).
13. **The workspace must be WSL's own case-sensitive file system.** A Windows folder is refused (D-178). Since D-242, `juno hook check` also confirms, from the superblock, that the ext4 holding it has case folding switched off entirely (property 23; residual 52).

**Verification of a task (mode A, D-067)**
14. **A write that keeps a file's size and restores its modification time** is not detected by the protected-path listing.

**Restarts (D-201, D-202)**
15. **Entries newer than a record's last anchor** (at most one interval, or since `juno-anchors` was last reachable) can be changed or removed before a restart without JUNO noticing; that includes a record created and deleted within that time. This is §3.4.1's stated bound, and the reason the interval is short.
16. **A grant's use is counted per journal.** The hook service and the gateway each keep their own journal, so a grant used through both is counted by each.
17. **A refused start is repaired by hand, by you as root** (D-206): you add a new journal folder to `/etc/juno/anchors.json` with the time of the recovery. Every count starts again there, and every grant signed before that time is refused, so nothing issued before the recovery can be used twice (`docs/operator-setup.md`, "When something goes wrong"). Only a power loss in the middle of one write is repaired without you (property 16).
18. **No command revokes a grant in a running service.** You withdraw a grant by removing or re-signing its file and restarting the service.
19. **A gateway call in flight when the gateway is killed** is in the journal as a call with no result.
20. **Which anchor repository a service uses is what root's file `/etc/juno/anchors.json` says** (D-208). Whoever is root on the machine, or you by mistake, can still pin the wrong repository or the wrong host key; JUNO checks that the file is root's and well formed, not that it names the right thing. Comparing the fingerprint with GitHub's page is your step (guide, Part D step 7).
21. **Two services on one journal folder: closed by D-221.** The hook and gateway services now hold the journal's lock from before they verify it until they stop, as the runner always did, so a second service (or a restore) on the same folder is refused. A lock left by a service that died is cleared only when its process is provably gone (D-069); otherwise you remove it by hand, as the refusal says.

**Recovery and the pinned repository (D-206 to D-208)**
25. **What the pin closes, and what it does not (the trust boundary, D-211).** The `juno-runner` account is part of JUNO's enforcement boundary: the services run as it and hold its journal, key and clone. What is closed: JUNO's installed service, started on a journal, clone, settings or git program that were replaced, refuses to start, and a run whose anchors could not be shown to be in the pinned repository stops every session. What is not closed, and is recorded rather than fixed: whoever takes over `juno-runner` can still stop the service, withhold entries (item 7), push extra anchors (item 9), set the service's node options so its own code runs inside JUNO's process (`NODE_OPTIONS` in the unit file it owns), or run a program of their own that is not JUNO at all and honours anything. What they cannot do: sign a grant (your key is off this computer except while you sign, item 1), or remove what is already in `juno-anchors` without trace: with the push key they can make an ordinary commit that removes or changes anchor files, but the repository keeps every commit (force pushes and branch deletion are refused), and the services and your check both refuse a history that ever did that (item 9; D-204, D-217). Anything they make the machine do differently from the journal and anchors you can check is found by your own check against a fresh copy from GitHub (guide, Part G step 7). That check, not the services, is what counts against a taken-over runner account, and it is run from your **admin** account (D-214): not as `juno-runner`, which owns its own settings, environment and folders, and not as root. You clone `juno-anchors` from GitHub into a folder of your own, root copies the journal and the journal's public key into it, and the check runs with a clean environment (`env -i`) using only `/opt/node22` and `/opt/juno`, reading the anchors' history as well as their files (property 20; residual 37). A review finding that needs control of the runner account is recorded here, not treated as a defect.
26. **A git command that runs longer than two minutes is ended and counts as a failure** (D-209), so an anchor repository that never answers refuses a start or stops sessions, as one that cannot be reached does. Every start fetches the whole repository, so as it grows a start takes longer; a repository that one day needs more than two minutes to fetch refuses starts (fail-closed) until it is moved to a new repository (guide, "When something goes wrong").
26a. **The local clone's own settings are not relied on.** Before every git command run in it, JUNO compares its settings with what JUNO's `git init` wrote; any change (for example a `url.*.insteadOf` or `core.sshCommand` added while the service runs) ends the command before git runs, and every session stops (D-213, round 7 finding F2). That comparison does not stop every way git can be made to read other settings (items 35 and 36); what JUNO relies on is the read-back below. The pinned repository's branch is asked of the pinned address with no repository at all, so nothing in the clone can answer for it, and every anchor and every listing is confirmed against it. A change made to the clone's *files* (not its settings) while the service runs is caught the same way when anchors are read: each file must be the one the pinned repository's commit names.
27. **A torn write is recognised by its shape:** the last line of exactly one record is incomplete, or complete with its head record not yet written, and everything before it verifies and agrees with the anchors. Someone who can write the journal could cut the last, not yet anchored, entry to look like that; that is inside item 15's bound, and it costs them every grant of every open session.
28. **"Open at the crash" errs on the strict side.** Every admitted session whose record shows no closing state counts as open, however long ago it last ran, so a torn write can exhaust grants of sessions you had finished with. A hook or gateway session records a closing state only when its time limit ends it.
29. **The recovery epoch is a time you type, and it decides which grants work.** A grant whose `issued_at` is earlier is refused, so the guide's dates are chosen to fit: the first journal's epoch a fixed early date (`2020-01-01T00:00:00Z`; your signing key is new, so no grant of yours is older), whenever you do Part D; the first grant yesterday; after a recovery, the epoch and the new grants' `issued_at` the same time (D-209, D-213; tested against the guide's text). JUNO refuses grants signed before it and refuses a pin that later says another time for the same journal; it cannot know that the time you typed is the time of the recovery. The guide has you take it from `date`.
30. **A session or task id is used once per anchor repository, across recoveries too.** Its anchors are in `juno-anchors` for good, so the same id on a recovered journal cannot be anchored and does not run. Use new ids after a recovery.
31. **A pin that names a local folder instead of an SSH address** is accepted by the services (JUNO's own tests use one) and refused by `juno hook check`. Run the check (guide, Part G step 4).
32. **A journal written before 2026-11-13 records no recovery epoch** and is refused under a pin; it needs the manual recovery once.
33. **After a manual recovery the old journal folder stays named in `/etc/juno/anchors.json`.** The guide keeps it as evidence; a service pointed back at it starts only if it still verifies against its anchors. Remove its line, as root, if you want no service ever to use it again.
34. **A git command ended by its time limit can leave its ssh running** until ssh notices its input has closed (D-209). It holds no lock JUNO waits on; the start or the anchor has already failed.

**Review round 8 and the setup follow-up (D-214, D-216)**
35. **A `.git/commondir` file in the clone gets past the comparison of its settings** (review round 8, R1). The runner account can add one naming another repository, whose settings git then reads. It needs control of the runner account (item 25). It fails closed: the reviewer's reproduction showed the read-back stopping every session, with nothing reaching the pinned repository.
36. **At a start, git reads the old clone's own settings while JUNO reads the clone** (`git ls-remote` and `git fetch` from it; review round 8, R2). It needs control of the runner account. The reviewer found no setting that runs a program there; a setting that changes what the clone offers makes the start refuse, because everything the clone offers must agree with what was fetched from the pinned repository.
37. **The independent check reads the journal's public key from the runner's folder** (root copies it with the journal; guide, Part G step 7). Whoever controls the runner account can replace that file. Every anchor already in `juno-anchors` was signed with the original key, and the check refuses a repository whose history ever removed, changed or renamed an anchor file (D-217), so those anchors are still there, and a replaced key makes the check fail, not pass (fail-closed); a session with no anchor at all fails the check too (`no_anchor`). Review round 1 of PR #54 showed this was not so before D-217: the check read only the files in the clone, so an ordinary commit replacing anchor files, with the journal and key replaced to match, passed it. Anchors added by such an attacker beside the honest ones fail too: each anchor must verify against the one key the check is given.
38. **The copy of JUNO in WSL is as good as your Windows account** (guide, Part A step 4 and Part E steps 11 and 12). It is the commit you checked on Windows, carried in one file, and each clone prints its hash for you to compare; anything that can change your Windows files before you copy them is item 1.
39. **The OpenSSH minimum was found by reading, not by running** (D-216). OpenSSH's release notes give 8.1 for signing with a key held by the agent; its source code shows 8.1 refusing the `-O hashalg=sha512` option JUNO passes, and 8.2 to 8.8 accepting it and signing with SHA-512, the default. Windows' OpenSSH is Microsoft's port and was not run here. Whatever a version does, a signature JUNO does not accept is refused by `grant verify` (guide, Part C step 3), and a failed signing tells you to send the line `ssh -V` prints.
40. **Undoing a hook session's folder needs the runner to be able to change the folder that holds it** (D-221, D-234; the undo runs in the sealed context, property 22, as the runner's identity with no capability, so the kernel's own access rules decide, D-228). The undo moves the session's folder aside with one rename in the folder holding it (`/srv/juno-work`) and makes it again there, so it needs `juno-runner` to read, change and enter that folder and every folder on the way, none of them sticky, set-user-ID or set-group-ID, on one file system. The guide gives `juno-runner` an access list on `/srv/juno-work`. The Claude Code user owns that folder and can take the access off (`chmod`, `setfacl`); JUNO's hook judges only the tools Claude Code calls, and allows such a command only if your session file lists it exactly. If it happens, **the next write into the session's folder is parked**, with the reason journalled (D-234 ruling 1: the check runs before every write), and a restore refuses with nothing changed, until you put the access list back or remove the bit, as `juno-agent` (the guide says how; D-226). A folder *inside* the session's folder no longer stops the undo, which moves it aside with the rest; a write below one the runner cannot change still parks (D-221, kept as the more restrictive reading). Admission refuses a reversible workspace the runner could not undo.
41. **An undo is one rename and then a rebuild** (D-234). It refuses before changing anything whenever it can tell it could not finish (the manifest, every file's bytes against its fingerprint, the way to the folder), and a rename that fails changes nothing. After the rename, the folder is made again from the checkpoint (at most 2,000 entries and 8 MB) through handles that never follow a link; a step that fails there (a full disk, a process of the Claude Code user making the folder at the same moment) leaves the new folder part made. It is then journalled as `failed`, with the reason and where the old folder is kept, whole, and can be run again. Nothing the session made is lost either way. While the service is stopped Claude Code is refused every call, so only another process of the Claude Code user could race it; one still running in the old folder keeps working in the moved-aside copy, never in the restored one.
42. **A restored file belongs to `juno-runner`, and comes back with a fixed mode** (D-228). The checkpoint records names and content, not owners or modes; the runner cannot give a file to another user. Every file a restore writes is `rw-rw----` (660) and every folder it owns `rwxrwx---` (770), so the access list keeps both changeable by the Claude Code user; a file's executable bit is not kept (make a script executable again after an undo). A folder of the Claude Code user's own keeps its own mode. A set-user-ID, set-group-ID or sticky bit is never taken and never recreated: a workspace holding one is not checkpointed, and a checkpoint naming one is refused at the restore (D-223, D-228).
43. **A gateway session has no reversible workspace** (D-221). The MCP server makes its own changes, outside any folder JUNO copies; so every write through the gateway is judged irreversible and parks unless its grant names the exact target. There is nothing to restore.
44. **Checkpoints taken before 1.5-field do not record their folder** and the host restore refuses them (D-221). Sessions admitted after the upgrade record it. A session admitted before the upgrade goes on, but its workspace is no longer reversible: a service rebuilding a session keeps a workspace reversible only when its journal holds that workspace's checkpoint taken in the service's own folder and the runner could restore it now, so that session's writes with an untrusted target park (D-224).
45. **The workspace belongs to the Claude Code user, so root never changes anything in it** (D-226), and JUNO's own copies and restores of it run sealed (property 22, D-228). A root command that walks or names a path there (`setfacl -R`, `chmod`) can be sent through a link the Claude Code user planted, and would then change files elsewhere, JUNO's own included. Every step of the guide that changes the workspace runs as `juno-agent`, which gains nothing by following a link; a test checks that no root step changes anything under it. Root's remaining steps there only read (`ls`, `stat`, `lsattr -d`, `getfacl`, `juno hook check`).
46. **A workspace with a link, a FIFO, a socket, a hard link, a special bit or a name that is not valid UTF-8 anywhere in it is not reversible** (D-228, D-231). JUNO takes only files and folders, with names it can record exactly, from a workspace; admission refuses such a reversible workspace and names the entry. Anything made after admission (an archive with Latin-1 names unpacked, say, a folder thousands of levels deep, or 200,000 files of an `npm install`) is no obstacle to the undo: it moves aside with the folder, which is made again from the checkpoint alone, so the folder's size and depth do not matter; the restore's case-folding check judges only the folder holding the session's folder, never the tree moved aside (D-234, D-237; CI's root-run runtime, whose AppArmor profile refuses to look up a path longer than about 4,096 bytes, is why a walk could never have reached the bottom: D-235). A session root removed altogether is made again. A project that needs links (a `node_modules` folder, a git clone made with hard links) can still be read and worked on in a session without `reversible_workspaces`, where writes park.
47. **The sealed context runs on `juno-runner`'s own container runtime and image** (`juno-workload:local`, which `make verify-rootless` builds). Whoever controls the runner account controls both (item 25). The program it runs is JUNO's own, read from root's `/opt/juno`, and the container's one mount is the workspace, so a change there reaches only what the Claude Code user can already reach.
48. **Checkpoints taken before D-228 are not restored** (they were not taken sealed; the restore and a restarted service refuse them). None was taken on your machine: only PR #60's unmerged commits took them.
49. **What JUNO still does on the host to the workspace, as the runner, is read names and kinds** (never a file's bytes): the read view that classifies a folder's read (D-156), which steps through folder handles that never follow a link and never opens a file; the boundary's resolution of each call's path, which asks the kernel where a path leads (it must, to judge it as the kernel does, D-113) and reads the type, mode and links of what it finds there, never its bytes, with the write check on the folders of that one path, their access, their file system and whether they fold case (two `lstat`s each, D-221, D-225, D-234, D-238), and a look (`lstat`, never a read) at each of the checkpoint's content files in JUNO's own store; and D-178's case-folding check (listing folders and reading their attributes), over the whole workspace at every start and admission, and at a restore over the folder holding the session's folder only (D-237); and opening the workspace folder itself to learn its identity, which the sealed program compares with what it was given (D-228). None of them writes, and none reads a file's content.
50. **Moved-aside folders stay until you remove them** (D-234). Each undo leaves the folder as it stood beside the restored one (`<name>.juno-undone-<time>-<hex>`, in `/srv/juno-work`), and JUNO never deletes or changes it: it is yours to inspect and remove (the guide says how). Until then it takes disk space, and it lies inside the workspace, where a later session can read it under its own grants; **every read of it, or of a folder holding it, counts at the highest class the session declares** (D-236), so it is never read at a lower class than the folder it came from. Renamed by the Claude Code user outside a governed session, it takes the class of its new place, as any file that user moves does.
51. **A mount that only root can make is not seen before a write** (D-235). JUNO tells a mount by its file system: a FUSE mount, which an ordinary user can make, is seen, and writes there or below it park. A bind mount of the same file system onto the session's folder, which needs root, looks like a folder; the undo's rename then fails, changing nothing, and the restore is refused with the reason. Root is trusted (item 25).
52. **A file system that can fold case is excluded by the verified install, not by every write** (D-241, D-242). Review rounds 12 to 14 (D-238 to D-240) each found a way for the Claude Code user, on an ext4 made with the `casefold` feature, to empty `/srv/juno-work` and give it the case-folding attribute, so that the undo would refuse while writes proceeded. Each was fixed, and the checks before every write stay (a second layer). Since D-242 such a file system is refused before any session: `juno hook check`, run as root, reads the superblock and refuses one with `casefold` on, and the guide has you read the same line with `dumpe2fs` (Part E step 12). Only root can switch the feature on (`tune2fs` writes the device, which only root can). Under your ruling 2 of D-241, a review finding that needs such a file system, root changing JUNO's files, or a non-native file system, all of which `juno hook check` checks for, is recorded here, not treated as a defect. **What the check does not see:** a file system switched to `casefold` by root after the check ran, or a workspace mounted by root afterwards (root is trusted, item 25); run the check again after any change root makes to the disk (guide, Part G step 4).
53. **A lock JUNO cannot prove dead still refuses** (D-243). A lock left in a PID namespace this process cannot see into, or whose owner's start time was not recorded while its PID is in use, or on a machine whose identity cannot be read, refuses the start and the restore. The refusal names the real file and says to remove it only after `pgrep -af 'juno[.]js (hook serve|gateway serve|checkpoint restore)|runner/src/main[.]js'` prints nothing; `pgrep`, too, sees only its own namespace. The restore never takes a lock over: after a crash, start the service once (it takes the lock over, records it and checks the journal), stop it, then restore. Start times are read from `/proc/<pid>/stat`, relative to the reader's time namespace: a process run as `juno-runner` in a time namespace of its own could make a live owner look replaced, but `juno-runner` can remove the lock anyway (item 25).
54. **The build check runs once, from the runner's own service file** (D-244). The file is `juno-runner`'s, like its other settings (item 25). It checks the copy before JUNO starts, not while it runs; the upgrade stops and disables the service before it touches `/opt/juno`. A `juno` command run by hand on a half-built copy may end with Node's own error instead of a refusal; it has written nothing by then.
55. **The service commands a refusal gives are run against a real user manager with a stand-in program** (D-247). In CI's rootless jobs, `systemctl --user stop|start|status juno-hook.service` are run exactly as the restore gives them, against a unit of that name whose program holds a real journal's lock with JUNO's own lock code; the hook service itself, its refusals and its take-overs are proven in sealed containers, where no systemd runs. A machine where `juno-hook.service` is already installed (yours) is never touched by that test.
56. **A printable name that looks like another is shown as it is** (D-249). Refusals escape every character a terminal acts on, and every backtick, in a name JUNO did not choose, so no such name can start a line, hide text or look like a command JUNO gives; and no command JUNO gives holds anything but printable ASCII. A name made of look-alike letters is still shown in prose as those letters.
57. **The fix for a special bit in the workspace is a guide command over the whole of `/srv/juno-work`, not one entry** (D-252). Since no refusal names a workspace entry inside a command (D-251), the guide's fixed command removes every set-user-ID, set-group-ID and sticky bit there, as `juno-agent`, which can change only its own files; an entry another user owns stays as it is, and the guide says to send the agent that line rather than use `sudo` alone.
58. **The weekly report counts what the journal records, as it records it** (D-254). A call the hook parked before a capability was judged is counted under its tool (`tool Bash`, `tool Write`); its program is the first word of the command as Claude wrote it; a write parked as outside the workspace has no target in the journal (JUNO records only which field was outside), so it is counted as `(not recorded: …)`. Calls passed to the gateway are counted here as passed; the gateway's own journal holds its decisions, and the report is run on that journal for them.

**Closed during Slice 1.5** (recorded earlier as residuals, now fixed): the runner's clone of `juno-anchors` and its setting for where it pushes being on the host, so that a journal replaced together with them started as new (items 22 and 24, closed by D-206 and D-208: the repository and GitHub's host key are pinned in root's own file, every start fetches from there and compares, and only root can add a journal folder); a restarted hook or gateway service forgetting grant use and admitted sessions (D-200, closed by D-201 and D-202: every service verifies its journal against its anchors at start and rebuilds from it); two services of one runner pushing anchors to the same repository at once (D-199); symlinks in scope checks (D-047, closed by D-113); hard links (D-156, closed by D-157); an anchor committed but never pushed being counted after a restart (D-126, closed by D-198); hook and gateway journals that were never anchored (closed by D-198).
